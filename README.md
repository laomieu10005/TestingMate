# Testing Mate v5.1

Testing Mate is a Windows-friendly Python GUI for C/C++ test-generation and coverage closure. It analyzes source files or a `compile_commands.json`, generates GoogleTest or CppUTest harnesses, runs them under MSYS2/MinGW, collects Clang/LLVM coverage, and writes audit-ready reports for C0, C1, and native LLVM MC/DC evidence.

The tool is designed to be deterministic first. Local Ollama refinement is optional and is used after deterministic analysis, generation, or report parsing has already produced concrete coverage feedback.

## Key Features

- Source input by file, folder, or `compile_commands.json`.
- Clang-first analysis with internal fallback when Clang parsing is unavailable.
- GoogleTest and CppUTest backend generation.
- Automatic backend build/run with retry-based oracle and mock fallback patching.
- C0/C1 coverage from Clang/LLVM line and branch coverage.
- MC/DC coverage only from native LLVM MC/DC records generated by `-fcoverage-mcdc`.
- Coverage-gap workflow with `Add Gap Cases` for uncovered line, branch, and MC/DC obligations.
- Manual testcase popup for adding review-only steps or direct C++ harness-body code.
- Interactive HTML report with coverage cards, obligations, backend output, embedded LLVM links, and dark/light theme toggle.
- Optional Ollama refinement from report evidence.
- ISO 26262 method-profile metadata for QM and ASIL A/B/C/D.

## Requirements

### Python

Use Python 3.10 or newer.

Required Python packages are mostly from the standard library. For development/regression testing, install `pytest`:

```powershell
python -m pip install pytest
```

### MSYS2 / MinGW / Clang

Testing Mate expects a Windows MSYS2 toolchain. The default root is:

```text
C:\msys64\mingw64
```

If this root is not found, the GUI asks you to select the MSYS2 `mingw64` folder. You can also override the location before launching:

```powershell
$env:TESTMATE_MINGW_ROOT = "C:\msys64\mingw64"
python .\TestingMate.py
```

Recommended packages for MSYS2 CLANG64:

```bash
pacman -S --needed \
  mingw-w64-clang-x86_64-cmake \
  mingw-w64-clang-x86_64-ninja \
  mingw-w64-clang-x86_64-clang \
  mingw-w64-clang-x86_64-llvm \
  mingw-w64-clang-x86_64-compiler-rt \
  mingw-w64-clang-x86_64-gtest \
  mingw-w64-clang-x86_64-cpputest
```

Recommended packages for MSYS2 MINGW64:

```bash
pacman -S --needed \
  mingw-w64-x86_64-cmake \
```

## Quick Start

From the repository root:

```powershell
python .\TestingMate.py
```

The package entry point opens the same GUI:

```powershell
python -m testing_mate
```

Basic workflow:

1. Add inputs with `Add Source`, or select a `compile_commands.json` with `Compile DB`.
2. Select coverage mode: `C0/C1` or `MCDC`.
3. Select test level: `UT`, `IT`, or `ST`.
4. Choose backend: `GoogleTest` or `CppUTest`.
5. Keep `Preprocess source first` enabled unless it breaks project-specific macros/includes.
6. Set include directories and defines manually when not using `compile_commands.json`.
7. Set `Retry` from `0` to `5`. This controls automatic expected-value and mock-expectation fallback patching after a failed backend run.
8. Click `Generate`.
9. Click `View Report` to open the latest generated HTML report.
10. Use `Add Gap Cases` or `Add Manual Testcase` to close remaining uncovered obligations.

## Current Pipeline

```text
C/C++ files, folders, or compile_commands.json
  -> optional preprocessing
  -> Clang AST analysis
  -> internal analyzer fallback when Clang cannot parse
  -> code database generation
  -> test-vector generation
  -> GoogleTest or CppUTest harness generation
  -> backend build and execution
  -> expected-value/mock fallback retry loop when enabled
  -> Clang/LLVM source-based coverage collection
  -> Testing Mate JSON/CSV/markdown/HTML reports
  -> optional coverage-gap generation
  -> optional manual testcase insertion
  -> optional Ollama report-driven refinement
  -> rerun and refreshed report
```

## Input Model

Testing Mate accepts:

- Source files: `.c`, `.cc`, `.cpp`, `.cxx`
- Header files: `.h`, `.hh`, `.hpp`, `.hxx`
- Source folders scanned recursively
- `compile_commands.json` from CMake/Ninja or another build integration

Folder scanning skips common generated/build folders, including `.git`, `.svn`, `.hg`, `.idea`, `.vscode`, `build`, `out`, `dist`, `cmake-build-debug`, `cmake-build-release`, `node_modules`, `__pycache__`, `generated`, and `gen`.

For production use, prefer `compile_commands.json`. It provides real include paths, defines, source files, and compiler context, which makes Clang analysis and harness generation much more reliable.

## GUI Actions

### Generate

Runs analysis, generates testcases, writes backend artifacts, builds/runs the selected backend, collects coverage, and refreshes reports. The current GUI always runs the backend after generation.

### ReTest

Reuses the existing generated backend environment, reruns manually edited or previously generated testcases, recollects backend coverage, and refreshes reports.

### View Report

Opens the latest generated HTML report, or the selected report file if one was chosen in the LLM/report input field.

### Add Gap Cases

Adds deterministic candidate cases from current uncovered coverage evidence. Select an uncovered row in the coverage table to target one function/line/metric, or leave no row selected to generate candidates for all planned gaps.

Supported gap evidence includes:

- Uncovered C0 line obligations.
- Uncovered C1 branch/decision obligations.
- Uncovered MC/DC obligations when native LLVM MC/DC evidence is available.

After adding candidates, Testing Mate rewrites the backend harness, reruns it, recollects coverage, and regenerates the report.

### Add Manual Testcase

Opens the manual testcase popup after a first `Generate` or `ReTest` has loaded function information.

The popup supports two modes:

- `Steps Only`: stores review/manual execution steps in the testcase metadata. This is useful for audit notes, manual closure evidence, or cases that require human review.
- `Harness Code`: inserts user-written C++ code directly into the generated `TEST` body. Use this mode when you want to add explicit calls, fixture manipulation, and `EXPECT_*` or `CHECK_*` assertions.

You can also click an existing testcase row to open the same popup with a corresponding template. The popup provides:

- Test ID.
- Source.
- Function.
- Coverage classification.
- Mode.
- Description.
- Preconditions.
- Values JSON / harness inputs.
- Steps or direct C++ test body.
- Expected result.

Supported Values JSON keys include normal parameter names and internal keys such as:

```json
{
  "param_name": "0",
  "__expected_return": "0",
  "__expected_output.out_param": "1",
  "__expected_global.global_symbol": "0",
  "__expected_calls": "DependencyA,DependencyB"
}
```

For direct code insertion, the generator stores the code in `__manual_action_code` and emits it inside the generated test body between manual block comments.

## Analysis Engine

For each function, the analyzer tries to extract:

- Function name, return type, parameters, and source line range.
- Local variables and globals read/written when available.
- Function calls and external dependency hints.
- Conditions from `if`, loops, switches, and decision expressions.
- Return paths and path hints.
- Data-dependency hints.
- Mock/stub requirements.

Primary analysis uses Clang. If Clang is unavailable or parsing fails, Testing Mate falls back to its internal analyzer and records that in `<source>_code_database.json`.

## Coverage Modes

### C0/C1

- C0 comes from LLVM line coverage.
- C1 comes from LLVM branch coverage.
- Generated-vector C1 evidence may be used as engineering feedback when backend branch counters are not available.
- If no branch/decision obligations exist, C1 is marked complete by definition.

### MC/DC

- MC/DC is claimed only from native LLVM MC/DC coverage records.
- Generated vectors, LCOV branch counters, and gcov branch counters are not treated as official MC/DC proof.
- The generated CMake harness enables `-fcoverage-mcdc` when LLVM coverage is used.
- If LLVM coverage exists but no MC/DC records are exported, MC/DC is shown as `N/A` with a reason.
- If no branch/condition obligations exist, MC/DC is marked complete by definition.

Generated testcases are useful engineering evidence, but executed backend coverage is stronger evidence. Review expected values and safety-critical oracles before using generated cases for sign-off.

## Test Levels

### UT

Unit-level tests for selected functions. This is the primary mode for GoogleTest and CppUTest harnesses.

### IT

Adds integration-oriented cases where calls, interfaces, pointer fields, and data-flow hints are detected. This is useful for AUTOSAR-style module interaction evidence.

### ST

Classifies generated evidence as system-level in metadata and reports. It does not replace a real system test environment.

## ISO 26262 Method Profile

Enable `ISO 26262 method profile` to add method-oriented cases and metadata based on the selected ASIL level:

- `QM`
- `ASIL A`
- `ASIL B`
- `ASIL C`
- `ASIL D`

The profile is generic. It is driven by analyzed function facts and policy tables, not by sample-project names. Executable methods include requirements-based tests, interface tests, fault-injection candidates, equivalence classes, boundary values, error guessing, C0, C1, and MC/DC-oriented vectors. Non-executable methods remain audit/review evidence.

## Backend Generation

Testing Mate generates runnable harnesses for:

- `GoogleTest`
- `CppUTest`

Each backend writes:

- Copied target source/header files.
- Project-linked source files needed by the selected harness.
- Generated test file.
- Generated stub source/header under `stub/src` and `stub/include`.
- `CMakeLists.txt`.
- `run_gtest.sh` or `run_cpputest.sh`.

Generated stubs are based on declarations found from headers and analyzed call requirements. Stub files are excluded from target coverage intent; report metrics focus on production source coverage.

Mock behavior:

- CppUTest stubs use `CppUTestExt/MockSupport.h`.
- GoogleTest stubs expose generated GMock-compatible declarations in `stub/include/stubs.h`.
- Mock parameters and return values follow the best available function declaration.
- When no declaration is visible, Testing Mate emits a reviewed fallback stub type so the harness remains buildable.
- Generated expectations are path-aware when call guards can be evaluated.

After a failed backend run, the fallback loop can:

- Update expected values from parsed expected/actual assertion failures.
- Remove redundant mock expectations that were never fulfilled.
- Add missing expectations for unexpected mock calls.
- Rerun the backend up to the GUI `Retry` value, capped at `5`.

## Coverage Collection

Default coverage uses Clang/LLVM source-based coverage. Generated artifacts include:

- `coverage.profdata`
- `llvm_report.txt`
- `coverage.json`
- `coverage.llvm.json`
- `llvm_html/index.html`

The generated CMake harness builds with:

```text
-fprofile-instr-generate
-fcoverage-mapping
-fcoverage-mcdc
```

The runner uses:

- `llvm-profdata merge --sparse`
- `llvm-cov report -show-branch-summary`
- `llvm-cov report -show-mcdc-summary` when supported by the installed `llvm-cov`
- `llvm-cov show -format=html -show-branches=count -show-mcdc` when supported
- `llvm-cov show -show-mcdc-non-executed-vectors` only when supported
- `llvm-cov export -format=text`

The runner checks whether the installed `llvm-cov` supports newer MC/DC flags before using them. If the flag is not available, the runner prints an info/warning message instead of passing an unsupported option.

Legacy LCOV can be requested for C0/C1 only:

```bash
export TESTING_MATE_COVERAGE_BACKEND=legacy_lcov
```

LCOV/gcov branch counters are never used for MC/DC.

## Generated Artifacts

For each selected source file, Testing Mate writes artifacts under:

```text
TestMate_out\<source-or-project>\<backend>\
```

Important files:

- `<source>_code_database.json`: analyzer facts, calls, variables, paths, dependencies, and mock requirements.
- `<source>_analysis.json`: functions, parameters, conditions, and generated cases.
- `<source>_enhancement_request.json`: compact handoff for LLM/report-driven optimization.
- `<source>_<backend>_cases.csv`: audit-friendly testcase export.
- `<source>_summary.md`: generated summary and coverage metrics.
- `<source>.html`: main interactive Testing Mate report.
- `<source>_<backend>_audit_checklist.md`: review and closure checklist.
- `<source>_gtest\` or `<source>_cpputest\`: backend CMake harness.
- `<source>_gtest\coverage.json` or `<source>_cpputest\coverage.json`: LLVM coverage export.
- `<source>_gtest\llvm_html\index.html` or `<source>_cpputest\llvm_html\index.html`: LLVM source coverage report.

When multiple files are selected, Testing Mate also writes:

```text
all_files_report.html
```

## HTML Report

The generated HTML report includes:

- Source and backend identity.
- Function and condition counts.
- C0, C1, and MC/DC metric cards.
- Metric notes describing whether data came from executed coverage or generated-vector analysis.
- Coverage obligations table.
- Function/condition details.
- Uncovered gaps and backend failures.
- Links to LLVM source coverage artifacts.
- Captured run stdout/stderr.
- A `Switch Light Theme` / `Switch Dark Theme` button.

The theme preference is stored in browser `localStorage` under `testingMateReportTheme`.

## Ollama Refinement

Ollama is optional. Install and start it separately:

```powershell
ollama pull qwen2.5-coder:3b
ollama serve
```

Testing Mate does not use the LLM as the first analyzer. The LLM receives compact report-driven chunks after deterministic generation has produced cases and coverage evidence.

The GUI fields control:

- `Use local Ollama`: enable/disable refinement.
- `Model`: default `qwen2.5-coder:3b`.
- `Timeout`: per-request timeout in seconds; minimum `5`.
- `Target %`: target coverage percentage.
- `Rounds`: refinement rounds.
- `Report`: coverage/failure report to use as evidence.
- `Refine From Report & Run`: generate refined cases, rerun backend, and refresh reports.

Accepted LLM output must be strict JSON. Arrays named `test_cases`, `cases`, or `vectors` are accepted, including replies wrapped inside a `coverage_enhancement` object. Cases that reference unknown functions or invalid symbols are rejected.

Optional LLM stages can be configured:

```powershell
$env:TESTMATE_LLM_STAGES = "coverage_gap,oracle,negative"
```

Default stage:

```text
coverage_gap
```

Available stages:

- `coverage_gap`: close uncovered line/branch/MC/DC gaps.
- `oracle`: suggest expected output values for test oracles.
- `negative`: suggest robustness/security-oriented negative cases.

| Variable | Purpose |
|---|---|
| `TESTMATE_MINGW_ROOT` | Override the MSYS2 `mingw64` root used by the GUI. |

| `TESTMATE_OLLAMA_NUM_PREDICT` | Reduce or increase Ollama response length. Minimum is `128`. |
| `TESTMATE_OLLAMA_AUTO_PULL` | Enable automatic model pull if supported. |
| `TESTMATE_LLM_MAX_FUNCTIONS` | Cap number of functions sent to LLM refinement. |
| `TESTMATE_LLM_MAX_GAPS` | Cap number of coverage gaps sent to LLM refinement. |
| `TESTMATE_LLM_STAGES` | Comma-separated LLM stages: `coverage_gap`, `oracle`, `negative`. |

Example timeout increase:

```powershell
$env:TESTING_MATE_RUN_TIMEOUT = "1800"

```

```powershell
$env:TESTMATE_OLLAMA_NUM_CTX = "2048"

```

## Troubleshooting

### `MSYS2 bash was not found`

Install MSYS2 and verify these paths exist:

```text
C:\msys64\mingw64\bin
C:\msys64\usr\bin\bash.exe
```

If MSYS2 is installed somewhere else, launch the GUI again and select the correct `mingw64` folder when prompted, or set `TESTMATE_MINGW_ROOT`.

### Missing `clang`, `llvm-cov`, `llvm-profdata`, `cmake`, or `ninja`

Install the matching MSYS2 packages for your prefix. If the generated runner has access to `pacman`, it will attempt to install missing packages automatically.

### Missing Clang profile runtime library

Install the matching `compiler-rt` package:

```bash
pacman -S --needed mingw-w64-clang-x86_64-compiler-rt
```

or, for MINGW64:

```bash
pacman -S --needed mingw-w64-x86_64-compiler-rt
```

### `llvm-cov.exe report: Unknown command line argument ...`

Use the generated runner from this version. It checks MC/DC flag support before passing optional `llvm-cov` arguments such as `-show-mcdc-summary` or `-show-mcdc-non-executed-vectors`.

If the error persists, update LLVM/Clang in MSYS2:

```bash
pacman -Syu
pacman -S --needed mingw-w64-clang-x86_64-llvm mingw-w64-clang-x86_64-clang
```

### Coverage lines look wrong

- Regenerate and rerun so latest target-source filtering is used.
- Check that the selected source file matches the copied source inside the backend harness.
- Prefer `compile_commands.json` when macros/includes affect line mapping.

### MC/DC is `N/A`

- Confirm the backend is using LLVM coverage, not legacy LCOV.
- Confirm target sources are compiled with `-fcoverage-mcdc`.
- Confirm your installed LLVM version exports MC/DC records.
- Remember that LCOV/gcov cannot prove MC/DC in this tool.

### Generated tests compile but fail

- Check placeholder expected values.
- Inspect generated stubs under `stub/src` and `stub/include`.
- Increase `Retry` up to `5` if you want automatic oracle/mock fallback patching.
- Use `ReTest` after manual testcase or stub edits.

### Mock failures remain after retry

- Inspect `stub/include/stubs.h` for the mocked function signature.
- Check whether the real call is guarded by conditions that are not satisfied by the testcase.
- Set `Retry` to `0` when you want to inspect the first raw backend failure without automatic patching.

### Ollama timeout or memory errors

Use a smaller model and reduce prompt/output size:

```powershell
ollama pull qwen2.5-coder:3b
$env:TESTMATE_OLLAMA_NUM_CTX = "2048"
$env:TESTMATE_OLLAMA_NUM_PREDICT = "256"
$env:TESTMATE_LLM_MAX_FUNCTIONS = "4"
$env:TESTMATE_LLM_MAX_GAPS = "2"
```

## Limitations

Testing Mate generates a strong first pass, not a final safety certification package. Review is required for:

- Exact expected-result oracles.
- Pointers, arrays, structs, unions, and hardware registers.
- Complex macros and build-specific include behavior.
- External globals and side effects.
- Function pointers and callback-heavy designs.
- Coupled MC/DC decisions.
- Integration behavior across real RTE/BSW/MCAL layers.
- C++ parsing, which is accepted but still experimental compared with C.
- Manual `Harness Code` blocks, because they are inserted directly into generated tests.

Path generation is intentionally prioritized rather than exhaustive. The tool focuses on return paths, error paths, boundary paths, branches with calls, global writes, interface paths, diagnostic paths, and uncovered paths to avoid path explosion.

## Review Checklist Before Using Results

- [ ] Confirm the selected source and build context are correct.
- [ ] Confirm include paths and defines match the production build.
- [ ] Review generated stubs and mock expectations.
- [ ] Replace placeholder expected values with real oracles.
- [ ] Review all manual testcase code and steps.
- [ ] Attach generated HTML, CSV, JSON, and backend coverage artifacts to evidence records.
- [ ] For MC/DC, verify that the report cites native LLVM MC/DC evidence rather than generated vectors or LCOV data.
